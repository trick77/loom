Strava in loom, and per-user integrations

Every user connects its own accounts; no token is shared (§10–§13 rewrite tunewire and peeq to that rule). Each user's own Strava data (profile, every activity, laps, splits, efforts, streams, gear, routes, starred segments) is offered to the model by the loom-strava sidecar over MCP, read through the official OAuth API. Zwift rides arrive through Strava's automatic upload.

1 · Scope

In: everything the read API returns about the connected user: athlete profile + zones, totals, every activity (incl. Only Me and privacy-zone data), laps, splits, best efforts, segment efforts, streams, gear, own routes (+ GPX), starred segments and the user's own efforts on them.

Out: other athletes' data of any kind: clubs, club feeds, kudoers, comment text, segment explore, leaderboards. Only counts (kudos_count, comment_count) stay. No write scopes (activity:write, profile:write). No Zwift API, no Apple Health.

Strava API Agreement (effective 2026-06-01): a user's data "can only be displayed or disclosed … to that user". One connection per user, read only by that user, satisfies that. §4.4: delete all Strava data on termination → disconnect revokes the token and deletes the row. The agreement has no AI clause (the 2024 training ban is gone).

3 · Open decisions

D1 · Who connects

Decided (2026-11-03): every user has its own token and its own data, never shared. BACKEND_STRAVA_USERS (loom user ids, comma-separated) says who may use Strava. Each listed account sees Settings → Strava, connects its own Strava account and gets the tools over its own data only. Unlisted: settings 404, no tools (RestrictUsers + Users).

Rule for every personal-data integration (§10): a _USERS list grants access, it never shares one person's token. The sidecar keeps one connection per loom user id; caches keyed by user id.

Listed but not connected → a call answers "connect Strava in Settings → Strava". Strava's athlete capacity (1 by default, 10 without review) must cover the listed users who connect.

D2 · Live reads vs local mirror

Decided (2026-11-03): v1 live reads + in-memory cache; history mirror later.

  • Live + cache: activity detail and streams are effectively immutable → cache 24 h (LRU, ~300 activities); list 5 min; profile/zones/gear 1 h. "Analyse my last ride" = 3 calls; "my last 20 rides" = 1. Fails at "best 20-min power across 2025": that needs streams of every ride (hundreds of calls).
  • Mirror (later): backfill all summaries into the sidecar's own store, keep fresh via Strava webhook (one subscription per app, callback must echo hub.challenge within 2 s, events create/update/delete + deauthorization). Adds a query_activities tool with arbitrary filters/aggregates over the whole history, and slowly backfills streams within the daily budget for power-curve / trend questions. Costs: a store in the sidecar, a public unauthenticated webhook route (loom forwards it), a background worker.

D3 · Streams: summarise in Go, or also hand raw data to run_python

Decided (2026-11-03): summary in Go in the sidecar, always set against the user's recent activities (§6). Raw streams (~10k points × 11 series per ride) never reach the model; they reach run_python only as CSV for charts (§6a).

D4 · Classifier category

Decided (2026-11-03): new category training ("the user's own workouts, rides, runs, training load, fitness progress"), like music in #711. Gate the server on training + health.

Tradeoff: health's block ("careful flowing prose … never diagnose … see a professional") is wrong for "how far did I ride last week". Ungated would put ~12 schemas into every turn of every connected user. A new category touches the classifier prompt for everyone (one more gloss).

D5 · Token storage

Settled by D6: tokens live in the sidecar's /data/state.json (0600), one entry per loom user id, like tunewire. loom stores and logs none; no loom migration.

D6 · In-process vs sidecar

Decided (2026-11-03): sidecar loom-strava. Rule from now on: every integration is a sidecar. backend/cmd/loom-strava, image loom-strava, compose service + profile strava, Containerfile, uid/gid 65532. Best-effort like tunewire: loom boots without it and offers the tools while it answers. Client id + secret and every Strava token stay in the sidecar; loom only holds the service bearer.

4 · Connection (PR 1: strava: connect account)

Config

  • loom: BACKEND_STRAVA_URL (empty = off), BACKEND_STRAVA_TOKEN (service bearer, ≥ 32 chars, required with the URL; stravaProblem like tunewireProblem), BACKEND_STRAVA_USERS (list, r.List; empty serves nobody). .env.example.
  • sidecar: STRAVA_TOKEN (same bearer), STRAVA_CLIENT_ID, STRAVA_CLIENT_SECRET; /data volume.
  • Redirect URI = loom's PublicURL + /api/strava/callback: the browser comes back to loom, never to the sidecar.

Sidecar state

/data/state.json (0600, written atomically): users: {<loom user id>: {athlete_id, athlete_name, scope, access_token, refresh_token, expires_at}}. Every route acts only on the X-Loom-User entry (§11).

Token refresh (sidecar)

Refresh 5 min before expires_at or on 401, serialised by a per-user mutex, new pair persisted before use (the old refresh token dies at once). invalid_grant → status expired, tools answer "Strava sign-in expired: reconnect in Settings → Strava".

UI

StravaPanel in Settings next to Apple Music (listed users, each its own connection): Connect / Reconnect / Disconnect, athlete name, a warning listing unticked scopes ("Only Me activities hidden" etc.). en + de strings. Connect is a top-level navigation, not fetch.

5 · Tools (PR 2: strava: activity tools)

Server strava = the sidecar's /mcp, BuiltIn, PerUser, RestrictUsers + BACKEND_STRAVA_USERS, TrustInstructions, categories per D4. Every call reads the caller's connection (§11), never anyone else's. Units follow the athlete's measurement_preference (metric: km, km/h, min/km, m). Dates in and out in the athlete's local time (start_date_local); arguments take YYYY-MM-DD. Every activity returned → structuredContent.sources with https://www.strava.com/activities/{id} (citation + "View on Strava" attribution). An mcp.json entry named strava replaces the built-in (file entries win by name), but never its per-user gating: the file cannot widen BACKEND_STRAVA_USERS or share a connection.

6 · activity_analysis output

  • Power (if watts): avg, max, normalized power, variability index, intensity factor + TSS (FTP from profile; omitted without one), kJ, mean-max curve at 5 s / 30 s / 1 / 5 / 10 / 20 / 60 min, time in power zones.
  • Heart rate: avg, max, time in HR zones, aerobic decoupling (power:HR or pace:HR, first vs second half), HR at the end of each hard effort.
  • Cadence, temperature, grade: avg / max; time stopped (moving).
  • Climbs: auto-detected sections ≥ 500 m at ≥ 3 % average grade: length, gain, avg grade, time, VAM, avg power + W/kg, avg HR.
  • Intervals: laps if the device wrote them; else efforts ≥ 30 s above 105 % FTP.
  • Series: per-km buckets (≤ 200 rows) of distance, time, speed, HR, power, cadence, altitude, grade, so the model can say where things happened. No latlng.

Pure Go, table-driven tests from recorded fixtures (a Zwift ride, an outdoor ride without power, a run, a swim without streams).

Compared with recent activities (always part of the answer)

  • Baseline: the user's activities of the same sport_type in the weeks before this one (arg, default 6, 1–26). Zwift (VirtualRide) and outdoor Ride stay separate unless mix_indoor=true. The activity itself is excluded.
  • Per metric (distance, moving time, speed/pace, elevation, avg HR, NP, IF, TSS, efficiency factor NP/HR or pace/HR, decoupling, best 5 s / 1 / 5 / 20 min power, kJ): this activity, baseline median, delta in %, rank ("3rd best of 14"), and a flag when it is the best or worst in the window.
  • Like for like: earlier activities on the same route (start and end within 200 m, distance ± 5 %) listed separately with the same metrics, so "faster than last time on this loop" is a direct comparison.
  • Load: TSS (or moving time without power) of the last 7 days against the weekly average of the window, plus that week's activity count, so the model can say "your heaviest week in the window".
  • Trend: per week of the window: count, distance, time, TSS, median EF; one row per week.

Cost and the metric store

  • Summary metrics (distance, time, speed, avg HR, avg/weighted watts, kJ, elevation) come from one list_activities page: 1 call for the whole baseline.
  • Stream metrics (NP, IF, TSS, EF, decoupling, power bests) need each activity's streams once. The sidecar keeps the computed metrics per activity on disk (/data/metrics/<loom user id>.json, a few hundred bytes each, no raw streams), so each activity's streams are fetched once ever. Deleted with the connection. Not the D2 mirror: only activities the user has already looked at or compared.
  • Cold start (6 weeks ≈ 15–25 activities): fetch missing streams newest first, stop at 50 % of the 15-min read budget; the answer marks the metrics it lacks ("NP baseline from 9 of 18 rides") and the next call fills the rest.
  • Metrics depending on FTP or zones are recomputed from stored inputs when the profile changes (FTP is part of the stored key).

6a · Charts through run_python (PR 3: strava: charts)

The sandbox has pandas + matplotlib; files in out/ become PNG artifacts. It has no network, and its inputs today are only thread documents. Missing piece: Strava data into the sandbox without storing it in loom.

Tool files (loom, generic)

  • An MCP tool result may carry CSV as standard MCP embedded resources ({"type":"resource","resource":{uri,mimeType:"text/csv",text}}). loom keeps them in memory for the running turn only, lists them in the run_python guidance as inputs (strava_<id>_streams.csv, …) and hands their bytes to the job like an upload.
  • Never persisted, never embedded into RAG, never shown in the chat; the model gets a one-line note per file, not the content. Caps: 4 MiB per file, 16 MiB per turn, csv/json only.
  • Next turn ("make it bigger") → the model calls the tool again; the sidecar's cache answers without Strava.
  • Turn-scoped, so per user by construction: no one else's turn can see the files.

D8 · Who draws: a chart module in the sandbox image, or the model writes matplotlib each time

Recommend: a small loomcharts module baked into the sandbox image (one function per chart above, reading the CSV columns, loom's Warm Editorial palette from ui/src/index.css, light + dark, 2× PNG). The model writes three lines (from loomcharts import ride_profile; ride_profile("strava_…_streams.csv", "out/profile.png")) and can still write raw matplotlib for anything else.

Tradeoff: every chart looks the same and is tested, and a call costs few tokens, but the sandbox image grows a module to maintain (pinned like the other libraries). Model-written charts need nothing new, but look different every time and spend tokens and the 60 s limit on plotting code.

Prompting: the training block says to offer a chart when a comparison or a ride profile would read better as one, and to draw it when asked; server instructions name the attached files and the chart functions.

7 · Prompting

  • Server instructions (trusted): read data with the tools, never estimate; cite each activity; compare with earlier periods when it helps; units as returned.
  • training block (D4): numbers first, short, a table for multi-activity answers, one useful observation; no medical diagnosis (health stays in charge of that).

10 · Rule: own token, own data

Personal data involved → every loom user has its own token and its own data. Never shared. A _USERS list only grants access; each listed user connects its own account. Exception: non-personal services that fetch non-personal data (context7, ipverse, …) keep one operator key.

Every integration loom builds is a sidecar (D6): its secrets, user tokens and caches live there, loom holds only the service bearer.

11 · Groundwork: the caller in every MCP call (PR 0)

  • runToolCall puts MCPPrincipal(t.user) into the call's context (mcp.WithPrincipal); scheduled runs carry t.user too. A per-user server called without a principal fails closed.
  • New ServerConfig.PerUser (json:"perUser"): the server serves each caller's own account. Implies RestrictUsers; config refuses perUser without a users list.
  • Own sidecars (tunewire): the remote client adds X-Loom-User: <user id> to each request. Trust rests on the service bearer token, which only loom holds; the sidecar never accepts the header without it.
  • File servers (peeq, any future one): each listed user pastes its own token in Settings → Connections; loom stores it per (user_id, server) (migration user_mcp_tokens) and sends it as ${USER_TOKEN} in the entry's headers ("Authorization": "Bearer ${USER_TOKEN}"). No loom user id leaves loom; the third-party server sees only its own token. Not set → the call answers "connect <server> in Settings".
  • Offered tools: a per-user server's tools are offered only to listed users who have connected (no dead schemas in the prompt).
  • Tests: two users, two tokens, each call carries only the caller's; no principal → refused; cache isolation.

12 · tunewire per user (PR A)

  • Sidecar state.json: users: {<loom user id>: {token, storefront, checked_at}}; developer token stays one (it is the web player's public token, no one's data). File stays 0600.
  • PUT/DELETE /token, GET /status act on the X-Loom-User account; /mcp/library reads that user's token; missing header → 400 on /mcp/library and the token routes.
  • Caches: the library artist list (artistsCache) keyed by user; releaseCache stays shared (catalog data by storefront + artist, no one's library).
  • loom: TunewireLibraryServerConfig gets PerUser; the settings handlers pass the signed-in user. Each listed user pastes its own cookie; status per user.
  • Docs: docs/tunewire.md "they share the one Apple Music token" → each listed account connects its own.

D7 · The token already in state.json

Decided (2026-11-03): no migration. The new sidecar ignores the old single token and rewrites the file in the per-user shape; each listed user pastes a fresh media-user-token.

13 · peeq per user (PR B)

  • loom side: the peeq entry gets "perUser": true and Bearer ${USER_TOKEN}; PEEQ_MCP_TOKEN goes away. Settings → Connections shows peeq to listed users.
  • peeq side (its own repo, not in this plan): it must issue a token per user and serve that user's own library behind it. Not checked from here; if peeq is one shared library today, that is a peeq change first.
